## Root-cause probe (PO-link race) — run AFTER the timed swarm script
Both VI failures below hit the identical symptom: after linking an Approved PO, the Post button
stayed `disabled` for the full 30s Playwright click-retry window, with **zero network request ever
sent** (no `POST .../post` in the trace — this is a client-side block, not a CRIT-1 500/23505).
Root-cause hypothesis: `vendor-invoices/new/page.tsx`'s PO-link `useEffect` (line ~99-123) fetches
`poDetail` async and then `setRows(poDetail.lines.map(...))` with **`categoryId: null`** for every
line — this REPLACES the entire rows array. If the category select is filled before that async
replace lands, the pick is silently clobbered and `canSave` (line 137-140, requires
`categoryId !== null` on every row) never becomes true again — no error, no visible cue.
Verified with a standalone probe (`swarm4-ap01-probe.mjs`, same login/PO/vendor, but with an
explicit 2.5s wait after selecting the PO before touching the category selects): Post became
enabled and **POST returned 200** — `{"vendorInvoiceId":12,"docNo":"07-2026-VI-0002",...,"totalAmount":1123.50,"vatAmount":73.50}`.
This confirms (a) the race is the real root cause, not a CRIT-1 numbering-path regression, and
(b) the underlying VI-post numbering path itself is healthy (2/2 real POSTs this round returned
2xx: probe's PO-linked VI-0002, and cycle 3's plain VI at /vendor-invoices/11 — zero 500/23505
observed in any VI POST that actually reached the server).
