- Deny-probes via direct URL: `/tax-invoices/new`, `/credit-notes/new`, `/payroll` (typed directly, not via sidebar — sidebar correctly omits all three for ap01).
- Code note for context (not from live probing, from reading the shipped i18n + spec comments): PV approval was changed from a hard DB creator≠approver constraint to **permission-based** approval (`purchase.payment_voucher.approve`) — a creator who *holds* that permission can legitimately self-approve by design (Ham decision, cont.77/88). The on-page hint next to where the Approve button would be still reads "ผู้อนุมัติควรเป็นคนละคนกับผู้สร้าง — ผู้ดูแลระบบ (super-admin) ข้ามได้" (approver should differ from creator; only super-admin can skip), which is *stale wording* for the new mechanism (it's not super-admin-only anymore, it's permission-based) — but functionally harmless for the AP_CLERK role specifically, since that role doesn't hold the approve permission and the button correctly never renders. Flagging as a LOW copy-accuracy note, not a security bug for this role.

The page's own on-screen text next to the (absent) button confirms the intent: "ต้องอนุมัติก่อนจึงจะ Post ได้ · ผู้อนุมัติควรเป็นคนละคนกับผู้สร้าง". This matches the mission's expected outcome. (`shots/ap01-06-pv-sod-denied-no-button.png`, before-state `shots/ap01-05-pv-sod-before.png`)

- **Tax Invoice actual write**: form renders (see HIGH finding above) but the real `POST /api/proxy/tax-invoices` is denied with 403 by the backend — the write itself is correctly gated even though the route/page is not.

- `POST /api/proxy/tax-invoices` → **403** — confirms backend permission enforcement despite the FE route gap (see HIGH finding above).

## Notes for Fable/consolidation
- The VI-post 500 (CRIT) is the highest-priority item — it's a core, in-scope AP Clerk action that is currently **completely broken** in prod for at least this vendor/category combination, reproduced twice with identical error bodies. Recommend correlating with API server logs around the two POST timestamps to get the real exception (the client-facing body is generically wrapped).
- The three route-level RBAC gaps (TI/CN/Payroll) share one root cause shape: **Next.js pages under `(dashboard)/` are reachable by any authenticated session regardless of role — only the sidebar link and the in-page action buttons are permission-gated, not the route itself.** Worth a single consolidated fix (route-level guard) rather than three separate patches, and worth checking whether other AP-Clerk-adjacent routes (sales-orders/new, quotations/new, receipts/new, etc. — outside this mission's scope) have the same shape.
