## §A — Public (browser-openable) PDF links [Ham #1] — FOOTGUN, opus-reviewed (design HARDENED 2026-07-08 — see Attempt log R1)

Problem: `get_*_pdf_url` returns `{BaseUrl}/api/v1/{doc}/{id}/pdf` which is X-Api-Key-only → browser click = 401.

### A.0 Verified code facts (do NOT re-derive these)
- **Tenant pipeline = the RLS/EF crux.** `TenantMiddleware` (`Api/Middleware/TenantMiddleware.cs`) is the ONLY thing that pins the Postgres RLS GUC. It reads `ITenantContext.IsAuthenticated` at the TOP of `InvokeAsync`; only if true does it `OpenConnection` + `SELECT set_config('app.company_id', …), set_config('app.is_super_admin', …)`, run `_next`, and reset in `finally` (with a `ClearPool` poison-guard). If `IsAuthenticated` is FALSE it **early-returns and never pins**. `AmbientTenantContext` (`Api/Tenancy/AmbientTenantContext.cs`) derives `IsAuthenticated`/`CompanyId`/`BranchId` **lazily from `HttpContext.User` claims** (`TenantClaims.CompanyId`/`BranchId`). The EF global query filter (`AccountingDbContext.cs:152` → `e.CompanyId == _tenant.CompanyId`) reads the SAME `ITenantContext`.
- **Pipeline order in `Program.cs`:** `UseRateLimiter()`(451) → `UseAuthentication()`(455) → `UseAuthorization()`(456) → `UseTenantContext()`(457) → endpoints.
- **Consequence (kills the old "endpoint builds a synthetic principal" fallback):** setting `HttpContext.User` INSIDE the endpoint handler is TOO LATE — `TenantMiddleware` (457) already ran and early-returned, so the RLS GUC is never pinned and the EF filter sees `CompanyId=0`. `AmbientTenantContext.SetCompany()` also does NOT help: that fallback is read ONLY when `HttpContext is null` (background-job scopes); a real request always has an `HttpContext`, so that branch is dead for requests.
- **No DataProtection is configured anywhere** (grep `AddDataProtection|PersistKeys|IDataProtector` over `backend/` = 0 hits; OpenIddict uses its own signing/encryption creds, not DP). `ITimeLimitedDataProtector` for §A is the app's FIRST DP consumer → it would fall back to the DEFAULT key ring. See A.4.

### A.1 Anonymous-request tenant context — REQUIRED mechanism (this replaces the vague "synthetic principal in the endpoint")
Add a tiny middleware **`PublicPdfTenantMiddleware`** and register it in `Program.cs` **immediately after `app.UseAuthentication()` (455) and before `app.UseAuthorization()` (456)** so it runs BEFORE `TenantMiddleware` (457). It:
  1. If `context.Request.Path == "/public/pdf"` AND the `t` query value is present:
     - `try { payload = protector.Unprotect(t); } catch { /* leave User anonymous — do NOT throw, do NOT 401 */ }`. Any failure (tamper/expired/garbage) ⇒ no principal set ⇒ the endpoint returns 404.
     - Parse `payload` = `docType|docId|companyId|branchId`. Build the identity with a **non-empty authenticationType** — this is load-bearing: `new ClaimsIdentity(claims, "PublicPdfToken")`. (`new ClaimsIdentity(claims)` with NO auth type has `IsAuthenticated=false`, and `TenantMiddleware` would then skip the pin — silent tenant-less read.) Claims: `TenantClaims.CompanyId=companyId`, `TenantClaims.BranchId=branchId` only (mirror `McpPrincipalFactory.Build`'s shape; **never** set `IsSuperAdmin`/`ApiKeyId`). Set `context.User = new ClaimsPrincipal(id)`; stash `docType`+`docId` in `context.Items` for the endpoint.
  2. `await _next(context);`
  Result: `TenantMiddleware` sees `IsAuthenticated=true`, pins `app.company_id` to companyId, and the EF filter reads the same company from claims → **BOTH layers engaged via the existing, poison-guarded pin/reset path** (no hand-rolled `set_config`, no `IgnoreQueryFilters`). `is_super_admin` stays false (claim absent), so RLS never widens.

### A.2 Token + endpoint
- `ITimeLimitedDataProtector` purpose `"teas.pdf-link.v1"`; payload `"{docType}|{docId}|{companyId}|{branchId}"`; TTL from `App:PdfLinkTtlHours` (default 24). **docType+docId come FROM the token, never a query param** → an attacker cannot swap the doc.
- Endpoint `GET /public/pdf?t={token}`: `.AllowAnonymous()`, `.RequireRateLimiting("public-pdf")`. Read docType+docId from `context.Items` (absent ⇒ `Results.NotFound()`). `switch(docType)` → the SAME service method the matching `/api/v1/{doc}/{id}/pdf` route calls (A.3), each `(id, ct) → byte[]`. Any service not-found / RLS-filtered row ⇒ 404.
- **Content-Disposition:** to render in the tab, emit `inline` explicitly (`context.Response.Headers.ContentDisposition = $"inline; filename=\"{name}.pdf\""; return Results.File(bytes, "application/pdf");`). Do NOT pass `fileDownloadName:` to `Results.File` — that forces `attachment` and downloads instead of rendering.

### A.4 DataProtection persistence (FOOTGUN — links die on every restart without this)
Because NO DP is configured and this is the first consumer, the DEFAULT key ring is used. On the self-contained pm2 deploy whose `unpacked/` is REPLACED each deploy, the default Linux location is `$HOME/.aspnet/DataProtection-Keys` — survives ONLY if `$HOME` is set, writable, and outside `unpacked/`. If not writable, keys are held **in memory**: every pm2 restart/redeploy invalidates ALL tokens (every public link 404s), and in pm2 cluster mode instances don't share keys (link minted by A rejected by B). REQUIRED in `Program.cs` (before `builder.Build()`):
```csharp
builder.Services.AddDataProtection()
    .PersistKeysToFileSystem(new DirectoryInfo(
        builder.Configuration["DataProtection:KeyPath"] ?? "/var/teas/dp-keys")) // stable path OUTSIDE unpacked/
    .SetApplicationName("teas");
```
Deploy-script note: create the key dir ONCE outside `unpacked/` (e.g. `$BASE/dp-keys`), chown to the pm2 user, and NEVER wipe it on deploy. `SetApplicationName` pinned so a future rename can't orphan the ring.

Draft documents where NO update service exists (tax_invoice, receipt) — **D3, design HARDENED 2026-07-08 (see Attempt log R1)**:

**D3.0 Verified pattern (quotation, the template `QuotationChainServices.cs:107-158`):** `UpdateDraftAsync` does `LoadAsync` (tracked, `.Include(Lines)`) → `if (q.Status != Draft) throw DomainException(...)` → set header fields → `db.RemoveRange(q.Lines); q.Lines.Clear();` (**delete-and-recreate lines — confirmed**) → reset `Subtotal/Vat/Total = 0` → re-derive each line's rate via `SalesLineBackstop.Resolve(...)` and amounts via `ChainMath.Line(qty, price, discPct, rate)`, re-accumulating header aggregates → single `SaveChangesAsync`. This is the SAME math the quotation CREATE uses (shared `ChainMath`/`SalesLineBackstop`), so create/update can't diverge.

**D3.1 TI/receipt compute is INLINE in create → EXTRACT, don't duplicate.** `TaxInvoiceService.CreateDraftCoreAsync` computes totals inline (`TaxInvoiceService.cs:205-225`): the `deriveLineTax` block (`SalesLineBackstop.Resolve` per line), then `var lines = srcLines.Select((l,i) => BuildLine(l, i+1, req.IsTaxInclusive))`, then `subtotal = lines.Sum(LineAmount)`, `taxable = lines.Where(TaxRate>0).Sum(LineAmount)`, `nontaxable = subtotal - taxable`, `vatAmount = lines.Sum(TaxAmount)`, `total = lines.Sum(TotalAmount)`. Receipt's create has its own inline compute. **Refactor first:** pull that "resolve rates + BuildLine + sum aggregates" block into a private method (e.g. `RebuildLinesAndTotals(entity, srcLines, req)`) that BOTH `CreateDraftCoreAsync`/receipt-create AND the new `UpdateDraftAsync` call. NEVER trust client totals — the request carries lines only; the server computes every amount.
- Guard code (copy quotation): `if (ti.Status != DocumentStatus.Draft) throw new DomainException("tax_invoice.cannot_edit_after_post", "...")` / `"receipt.cannot_edit_after_post"`. Surface verbatim as `McpE2Exception` in the tool (mirror create-tool error surfacing).
- **Server-controlled fields, NOT accepted from the client:** DocNo, Status, PostedAt, and **DocDate/TaxPointDate** (create pins these to `_clock.TodayInBangkok()`; `PostAsync` RE-pins at post — `TaxInvoiceService.cs:300-302`). The draft-edit must leave them server-derived, not take a client date.
- Reuse create's header validation on edit (customer exists, `ApiKeyBuBinding.Resolve` BU-lock, product-type master override, VAT-registered-customer completeness). Skip the numbering/period-gate that only the post path needs.

**D3.2 Concurrency (post vs edit) — CONFIRMED + IMPORTANT correction.**
- `PostAsync` DOES re-read inside a transaction: `TaxInvoiceService.cs:289` `BeginTransactionAsync`, then `291-294` re-load with `.Include(Lines)` + guard, snapshot line product codes while still DRAFT, then MarkPosted. **Confirmed** (the spec's "confirm" is satisfied).
- **The `Version` EF concurrency token is INERT — do NOT rely on it.** `Version` is `IsConcurrencyToken()` on TaxInvoice (`TaxInvoiceConfiguration.cs:68`) and Receipt (`ReceiptConfiguration.cs:50`), BUT it is only ever set to `0` at creation and is **never incremented** — not by app code, not by any SQL trigger (grep of `SqlScripts` finds no version-bump), and not by `AccountingDbContext.SaveChangesAsync` (which only stamps audit timestamps, `AccountingDbContext.cs:155-182`). With a static token value, two concurrent UPDATEs both match `WHERE version=0` → NO `DbUpdateConcurrencyException`. (The `570` comment claiming version "mutates after post" is aspirational — nothing mutates it.) So optimistic concurrency gives ZERO protection here.
- **The real backstop is the DB immutability triggers, and it holds BECAUSE `UpdateDraftAsync` always delete-and-recreates lines.** If a post wins the race (draft→POSTED committed first), the edit's line `DELETE`/`INSERT` fires trigger `582` (`fn_ti_lines_immutable`/`fn_receipt_lines_immutable`: parent now non-DRAFT → `RAISE check_violation`/SqlState 23514) → the whole edit transaction aborts, posted doc untouched. If the edit commits first (still DRAFT), post simply posts the newest draft — fine. **Therefore NO `SELECT ... FOR UPDATE` and no new locking is needed** — smallest correct fix is: keep the existing tx-wrapped post path + ALWAYS rewrite lines on edit.
- **HARD REQUIREMENT:** `UpdateDraftAsync` MUST `RemoveRange` all lines + re-add on every edit (never a diff / skip-if-unchanged optimization). That guarantees trigger `582` is the backstop even for a header-only edit — `583` (TI header) only catches CRITICAL-field changes, so a non-critical header-only edit racing a post could slip past `583`; always-rewriting lines closes it uniformly.

**D3.3 Trigger coverage (answers the spec's "582/583 cover the gap?" — receipts DO have equivalents).**
- Tax invoice: header = **583** (`fn_enforce_ti_immutability`, guards `OLD.status <> 'DRAFT'` → freezes totals + status transitions), lines = **582** (`fn_ti_lines_immutable`). Both confirmed.
- Receipt: header = **570** (`fn_enforce_receipt_immutability`, guards `OLD.status = 'POSTED'`), lines = **582** (`fn_receipt_lines_immutable`). So receipts ARE DB-backstopped — the service guard is NOT the only protection.
- Note (no fix needed here): `583` guards `<> 'DRAFT'` (POSTED **and** VOIDED) while `570` guards only `= 'POSTED'` — a VOIDED receipt header's critical fields aren't DB-frozen, but the draft-only tool can't reach a VOIDED row (its own guard blocks non-Draft), so it's unreachable from this feature.

- Expose `update_tax_invoice_draft`, `update_receipt_draft` [same scopes as their create tools].
- **Tests per edit tool:** (a) draft edit persists + server RECOMPUTES totals — send deliberately wrong client-suggested totals, assert stored totals = server math, not client; (b) editing a POSTED doc → clean `...cannot_edit_after_post` code (service guard, common path); (c) cross-tenant id → not-found (**same RLS-superuser caveat as §A.6 — assert under `SET ROLE pg_database_owner`**); (d) validation failure surfaces field errors; (e) **line-immutability race backstop:** post a draft, then run the queued edit against it → edit fails and the posted doc is unmodified. The race path throws `DbUpdateException` wrapping SqlState `23514`, which surfaces as 500 unless mapped — either map it in the tool to `McpE2Exception("mcp.doc_not_editable", ...)` (preferred) or document the 500 as acceptable; the test asserts NO mutation either way.
